## Bugs & risks

- [x] **Weekly-recap push notification computes XP/level from a stale, incomplete formula.** `supabase/functions/send-notifications/index.ts` lines 29-36 hardcodes an `XP` rate table that mirrors only a subset of `src/lib/xp.ts`'s `XP_RATES`, and `userLevel()` (lines 145-164) omits every sport dimension (basketball, pickleball, golf, disc golf, hiking, table tennis, chess, volleyball, spikeball, pool) and nutrition entirely. A user active in any of those 10+ categories gets an under-reported level/XP in their Monday recap notification — a third, silently-diverging copy of XP math beyond the documented client RPC/rawRows pair. Effort: M, Impact: 4.
- [x] **Seasonal XP silently excludes 10 categories.** `src/lib/xp.ts`'s `seasonAggregatesFromRpc` (lines 236-257) hardcodes `0` for `challenge_xp`, `goal_xp`, `measurement_count`, and all sport fields (`bb_*, pb_*, golf_*, dg_*, hike_*, tt_*, chess_*, vb_*, sb_*, pool_*`) because `get_xp_aggregates` only returns `_season` variants for a subset of columns (`migrations/phase7-nutrition.sql:56-145`). This is flagged as intentional in a code comment, but means the Home hero's season level under-counts real activity for anyone who plays any of the 10 sport pages — likely not the intended behavior for a "seasonal reset" feature. Effort: L (needs new SQL season columns + client wiring), Impact: 4.
- [ ] **`get_xp_aggregates`/`aggregatesFromRawRows`/edge-function XP have no shared source of truth.** Three independent hand-maintained copies of XP math exist: `src/lib/xp.ts` (`xpFromAggregates` + `aggregatesFromRawRows`), the SQL in `migrations/phase7-nutrition.sql`, and the edge function's local `XP` const. Adding a new `XP_RATES` category today requires updating 4-5 places (SQL all-time column, SQL season column, `xpFromAggregates`, `aggregatesFromRawRows`, edge function) with no compiler or test to catch a missed one. Document the checklist in `xp.ts` at minimum; longer term, consider a single JSON rates file consumed by both TS and (via codegen) the edge function. Effort: M for docs, L for real fix, Impact: 4.
- [ ] **All 40+ `.insert()` call-sites bypass the offline queue.** `src/lib/offlineQueue.ts` has no producer function (`enqueue`), so despite the PWA being installable and offline-capable, every write in `QuickLogSheet.tsx` (8 sites), `GameLogPage.tsx`, `TodayCard.tsx`, all `forms/Log*Form.tsx`, and every page with a log form (Records, Sleep, Books, Cardio, Water, Goals, etc.) fails outright when offline instead of queuing. This contradicts the "works offline as a PWA" pitch in CLAUDE.md for anything beyond static asset caching. Effort: L, Impact: 4.
- [x] **`meals` table nutrition data has no offline handling and no error boundary beyond a manual `isMissingTableError` check.** `src/pages/Nutrition.tsx` reimplements 42PXX-code sniffing inline (lines 36-41) rather than a shared helper — if other legacy pages need the same missing-table fallback, this logic is now duplicated. Grep for `42P01` across pages to confirm and centralize into `lib/utils.ts`. Effort: S, Impact: 2.
- [x] **Displayed leaderboard XP can silently go stale with no auto-sync.** `src/pages/Leaderboard.tsx` line ~211-213 shows a manual "(stale)" label and a "Sync XP" button rather than syncing automatically on load — a user who forgets to tap Sync appears under-leveled to others indefinitely. Consider auto-syncing on `Leaderboard` mount (already fetches `totalXP`/`level` from the store) since the write is idempotent. Effort: S, Impact: 2.
